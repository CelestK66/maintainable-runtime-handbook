# Why I Use PDF Endpoints: US/EU SaaS Shipping Labels With Explicit Retention

Short answer: for a US/EU SaaS generating shipping labels, I would put a stable, application-owned endpoint in front of the renderer, use a synchronous byte response only for small interactive jobs, and switch to an asynchronous artifact workflow for batches. Fidelity is a release gate, latency is a measured budget, and retention is an explicit per-job field rather than a provider default.

The important choice is not “which PDF company wins?” It is where the system draws boundaries around order data, rendering, and stored output. A beautiful label that leaks an address into long-lived logs has failed. So has a private design that silently changes a barcode, clips the destination, or makes a warehouse operator wait without a useful job state.

My decision rule is blunt: keep the rendering contract replaceable, keep personally identifiable data out of URLs, and retain generated bytes for the shortest period the actual workflow requires. The catch is that this adds an application-owned adapter and test suite. A very small team with one low-volume template may reasonably keep a direct renderer integration until that extra layer pays for itself.

## What should a US/EU SaaS ask of PDF endpoints for shipping labels?

Start with the output contract. A request should identify a versioned template, carry validated order fields in the body, select a declared page profile, and include an idempotency key. The response should either contain the PDF bytes with the correct media type or return a job identifier whose state can be polled. Don't place a recipient name, street address, phone number, or order payload in the path or query string.

I treat fidelity as binary at the template boundary. The page dimensions, margins, fonts, barcode placement, line wrapping, and fallback behavior are part of a versioned fixture. “Looks close” isn't a useful acceptance criterion when a few millimeters can move a machine-readable mark or push an apartment number onto an unintended line.

The request also needs operational semantics. Define what happens when the same idempotency key arrives twice, what input validation failure looks like, how clients distinguish throttling from a rejected template, and when an asynchronous result expires. For example, an adapter can reserve `422` for input that cannot satisfy the label schema and `429` for temporary admission control; these are contract choices, not claims about a third-party service. A renderer-specific status must not leak through as the application's public error model.

Privacy belongs in that same contract — not in a policy document that nobody reads during an incident review. Record the processing region selected for the job, the requested retention class, and an opaque correlation ID. Store the minimum order projection needed to render the label. If the workflow only needs recipient, destination, service level, and package facts, don't send invoice notes or unrelated account metadata.

I'm not sure one retention duration can fit every carrier handoff, dispute process, and customer agreement. Your mileage may vary. What can stay constant is the mechanism: name the retention class, enforce deletion through the artifact owner, and make the decision visible to operators without exposing the label content itself.

## Put one contract in front of three execution modes

The adapter below is intentionally generic. It doesn't assume a commercial API, and its two routes belong to the application itself: one submits a render job and one deletes an artifact. The example keeps addresses in a JSON body, chooses between immediate bytes and a queued job, and makes retention explicit.

```python
from dataclasses import dataclass
from typing import Literal, Protocol


@dataclass(frozen=True)
class LabelRequest:
    template_version: str
    order_id: str
    recipient: str
    address_lines: list[str]
    country_code: str
    page_profile: Literal["label_4x6", "a4"]
    retention: Literal["transient", "handoff_window"]


@dataclass(frozen=True)
class RenderResult:
    state: Literal["complete", "queued"]
    correlation_id: str
    pdf_bytes: bytes | None = None
    artifact_id: str | None = None


class LabelRenderer(Protocol):
    def render(
        self,
        request: LabelRequest,
        *,
        idempotency_key: str,
    ) -> RenderResult:
        ...

    def delete_artifact(self, artifact_id: str) -> None:
        ...
```

There are three useful execution modes behind that interface. A synchronous mode returns bytes for one interactive label when the render can fit inside the caller's latency budget. An asynchronous mode returns an opaque job or artifact identifier for batches, admission control, and retries. A self-managed mode runs the rendering process inside infrastructure the SaaS controls; it offers the most direct control over data placement and runtime behavior, but the team owns patching, fonts, capacity, and failure recovery.

Keep the caller unaware of those differences where possible. It should submit the same validated document model and receive the same error vocabulary. This is the part I care about most: swapping a renderer should be an adapter change plus fixture qualification, not a rewrite of order handling.

The browser boundary deserves separate treatment. If an operator downloads a completed label, browser code can represent the returned bytes as a `Blob`; MDN documents `Blob` as an immutable, file-like object of raw data. That is useful for a download flow, but it does not decide server-side retention. Revoking a browser object URL and deleting a server artifact are different lifecycle events, so model both.

## Fidelity, latency, privacy, and complexity need different tests

One score hides the failure that matters. I use four gates instead.

| Gate | Evidence before release | Reason to reject a mode |
| --- | --- | --- |
| Fidelity | Golden PDFs from versioned order fixtures, plus visual and machine-readable checks | Fonts, dimensions, wrapping, or marks differ beyond the team's declared tolerance |
| Latency | Distribution from representative single and batch jobs, measured through the application boundary | Interactive work misses its budget or batch work blocks request threads |
| Privacy and retention | Data-flow inventory, region selection record, deletion test, and redacted telemetry review | The team cannot explain where payloads or artifacts persist and who can retrieve them |
| Operational complexity | Runbook exercise covering retry, throttling, duplicate submission, and renderer replacement | On-call staff cannot diagnose a job without opening the document content |

The fidelity suite should use awkward data, not polished demo orders. One synthetic canary order can combine a long company name, a two-line street, an apartment, accented characters, a country-specific postal format, a missing optional phone number, and the largest package values the schema permits. Freeze that input and its template version beside the expected output. The test should inspect page geometry and compare the visual result, while a separate check reads the machine-readable mark and compares its decoded value with the fixture. It should also assert that required destination lines appear exactly once. If a reviewer approves an intentional wrapping change, create a new template version and expected file; don't overwrite the old expectation while old jobs can still reference it. This single unpleasant fixture is more revealing than a folder of short, ASCII-only addresses, and it gives a template migration a concrete pass or fail result without pretending pixel equality alone proves that a label works.

Latency needs two clocks. The first measures interactive time from application request to downloadable bytes. The second measures batch completion from accepted job to artifact availability. Separating them prevents a fast acceptance response from masquerading as a fast render. It also makes backpressure honest: once a queue crosses the team's threshold, reject or defer new work according to the public contract instead of letting requests linger ambiguously.

Fast isn't enough.

Retries complicate it.

For privacy, log states and identifiers, not payloads. Useful fields include template version, execution mode, processing-region choice, duration, byte count, outcome class, retry count, and an opaque correlation ID. Names, addresses, label URLs, and rendered bytes do not belong in routine application logs. Access to artifacts should be scoped and time-bound by the application, while deletion tests verify that the retention promise is executable rather than aspirational.

Operational complexity shows up at the edges: font packaging, template rollout, queue depth, duplicate jobs, partial batches, artifact cleanup, and support access. A managed endpoint transfers some runtime work away from the team, but the application still owns validation, privacy decisions, retry policy, and customer-visible behavior. Self-management may suit strict placement requirements or specialized rendering, although it is not suitable when the team cannot staff upgrades, capacity planning, and on-call response. Conversely, a managed mode is a poor fit when its documented processing or retention controls cannot meet the SaaS's agreements; in that case, keep rendering inside an approved boundary.

## Compare modes only after defining the gates

Once those tests exist, comparison becomes evidence collection rather than a feature checklist. Run every candidate mode against the same fixture corpus and the same application-owned endpoint. Capture raw observations, then make the decision using thresholds agreed by engineering, security, operations, and the people who print the labels.

A direct synchronous endpoint has the smallest conceptual flow and can work well for a single operator action. Its limitation is coupling: the caller's deadline now includes rendering, and retry behavior must avoid duplicate work. An asynchronous endpoint introduces job state and artifact cleanup, yet it isolates long or bursty work from request threads. Self-managed rendering gives the team direct control over the execution environment and data path, at the cost of owning the runtime. None is universally best.

I would choose synchronously rendered bytes for a proven small-label path that consistently meets the interactive budget. I would choose an asynchronous artifact path for multi-label batches or workloads that need deliberate admission control. I would choose self-managed execution only when control requirements justify the continuing operational load. These modes can coexist behind one contract, which is often cleaner than forcing every order through the same latency and retention policy.

One caution: don't multiply endpoints by template, region, carrier, and page size. Those are validated fields or routing policy inside the adapter. A narrow public surface makes authorization, audit, idempotency, and migration easier to reason about.

## Roll out with a reversible boundary

Begin with a shadow qualification pass using synthetic orders and the full golden corpus. Then route a small class of non-sensitive test work through the new adapter, compare output at the application boundary, and expand by template version. The release unit should be a template and page profile, not every label at once.

During migration, keep one authoritative artifact owner. Dual rendering is useful for comparison, but dual delivery can create duplicate labels and unclear deletion responsibility. Move creation first, verify observability and retention enforcement, then retire the old path after its remaining artifacts reach their declared expiry.

The final design is deliberately boring: one input model, one renderer interface, explicit execution mode, explicit retention class, and tests that treat visual output and data lifecycle as release criteria. That is the balance I want for shipping labels. It gives the SaaS room to change how PDFs are produced without changing what privacy, delivery, and support teams are promised.
